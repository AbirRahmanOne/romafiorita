1. PROJECT CONTEXT
══════════════════════════════════════
Brand: Roma Fiorita · https://romafiorita.com
Business: online flower and gift shop in Rome, Italy.
- Customers anywhere in the world order and pay online; delivery happens only inside Italy.
- Rome (own riders): same-day delivery. Customers can choose Standard (any time that day), a 2-hour window (+fee) or an exact time (±15 min, +fee), in 15-minute slots from 07:00 to 23:45, with per-slot capacity.
- Rest of Italy: next-day boxed delivery by courier, date only.

Trust model:
- a photo of the real bouquet is sent to the buyer before delivery
- all-in prices
- on-time delivery

Languages: IT and EN. Currency: EUR only.

Payments: Stripe, on an account in the owner's own name (business type "Individual", no VAT number yet).
- Statement descriptor: ROMAFIORITA.
- Website orders are AUTHORISED (held) at checkout and CAPTURED when the shop accepts the order. Declining releases the hold.
- Custom-order payment requests are captured immediately on payment.

Repos and domains:
- this repo = backend only, deployed at api.romafiorita.com
- storefront (Next.js) at romafiorita.com and admin (Vite React SPA) at admin.romafiorita.com are a SEPARATE repo that consumes this API through a TypeScript client generated from our OpenAPI schema. The OpenAPI schema is therefore a product in itself: accurate, typed, stable.

Stack (keep it; justify any change): Python 3.12, FastAPI, Pydantic v2, SQLAlchemy 2.0 (async), Alembic, PostgreSQL 16, Redis, arq background jobs. Hosting on Render (Frankfurt).

Third-party services:
- Stripe (payments)
- Resend (email from ordini@romafiorita.com)
- Cloudflare R2 (images)
- Google Search Console API (SEO insights)

3. TARGET ARCHITECTURE & CONVENTIONS
══════════════════════════════════════
Layout (migrate gradually towards this):
app/
  main.py (app factory, lifespan) · core/ (config via pydantic-settings, logging, security, errors, ids, time, money)
  api/v1/ (routers: public/, admin/, webhooks/) · deps.py (db session, current_user, role guards, pagination)
  domain/ (pure business logic: delivery engine, pricing, order state machine, without FastAPI or DB imports)
  services/ (use cases orchestrating repos + domain + integrations)
  repositories/ (SQLAlchemy queries only) · models/ (ORM) · schemas/ (Pydantic API models)
  integrations/ (stripe, resend, r2, search_console, whatsapp: thin, mockable adapters behind interfaces)
  workers/ (arq tasks + cron) · tests/ (unit, integration, contract, e2e-api)

Rules:
- Money: integer cents everywhere (DB, schemas, Stripe). Never floats. One money helper.
- Time:
  - store timestamptz in UTC
  - business rules in Europe/Rome via zoneinfo
  - never use naive datetimes
  - DST-safe slot generation (test the March and October switches)
- IDs: UUID primary keys internally; public order number RF-YYYY-NNNNN (sequence per year, gap-tolerant); secure random tokens for tracking and payment links.
- API:
  - versioned under /v1
  - consistent error envelope {error: {code, message, details, request_id}}
  - cursor or limit/offset pagination with a max page size
  - filtering and sorting whitelists
  - explicit response_model on every route
  - proper status codes
  - an Idempotency-Key header on POST /checkout, /pay/{token}/intent and admin money actions
- OpenAPI:
  - meaningful operation_ids (for client generation), tags, and examples on key schemas
  - enums as string enums
  - no `Any`
  - export openapi.json in CI and fail on unintended breaking changes (e.g. oasdiff)
- Config: everything via env (pydantic-settings), validated at startup; .env.example kept complete.
- Logging: structured JSON with request_id/correlation_id; never log card data, tokens, secrets or full addresses.
- Every DB change goes through Alembic: reversible, data-preserving; no destructive migration without a backup step and explicit approval from me.

4. DOMAIN — TARGET SPEC
══════════════════════════════════════
A) Catalog
- Product: slug (IT/EN), name/description IT/EN, occasions, category, images, SEO title/description IT/EN, active, sort order.
- EXACTLY three variants per product, tier enum STANDARD | PREMIUM | LUXURY. Each variant has:
  - price_cents
  - description IT/EN, images
  - active
  - is_default (exactly one per product)
  - same_day / exact_time eligibility
  - optional stock
- Constraints: unique (product_id, tier); at least one active variant; DB-level checks where possible.
- Add-ons (card, teddy, balloon, vase) with prices. No alcohol or food at launch, enforced by category config.
- Public endpoints return only active items, localised by ?locale=it|en with fallback.
- Bulk price change with preview (dry-run) and apply, audited.

B) Delivery engine (pure domain module, fully unit-tested)
- Zones by postcode (CAP): Rome CAPs 00118–00199 (configurable table) are ROME; every other valid Italian CAP is NATIONAL; anything else is rejected.
- Delivery types:
  - ROME_STANDARD, ROME_WINDOW, ROME_EXACT
  - NATIONAL_COURIER (next working day; no Sundays/holidays, configurable)
- Settings (DB, editable by admin):
  - same-day cut-off per zone
  - exact-time minimum notice (e.g. 3h)
  - window and exact-time fees
  - slot length 15 min, operating hours
  - blocked dates
  - peak-day capacity
  - capacity per slot / per rider
- Slot availability = capacity − confirmed or held bookings.
- Booking a slot must be race-safe: transactional, SELECT … FOR UPDATE or an atomic counter with a constraint. Two simultaneous checkouts can never overbook.
- Slot reservations expire if payment isn't completed within N minutes.
- Endpoints: /delivery/check, /delivery/slots. Responses state times in Europe/Rome and include ISO timestamps so the frontend can show the buyer's local time.

C) Pricing
- Server-side quote only: variant price + add-ons + delivery/time fee − discount = total, all in cents.
- The client never sends prices; it sends IDs only.
- Discount codes: percent or fixed, expiry, usage limit, per-customer limit.

D) Orders & lifecycle (explicit state machine in domain/, transitions table-driven)
- PENDING_PAYMENT → NEW (payment authorised) → ACCEPTED (payment captured) → AWAITING_PHOTO → PHOTO_SENT → APPROVED → OUT_FOR_DELIVERY → DELIVERED
- Side states: DECLINED (hold released or refunded), CANCELLED, REFUNDED, PARTIALLY_REFUNDED, PROBLEM, PAYMENT_REQUESTED (custom orders), EXPIRED
- For each transition, define:
  - allowed roles
  - guards (e.g. a photo is required before PHOTO_SENT)
  - side effects (emails, SSE event, capture/cancel the Stripe hold, audit log)
- "Accept with change": proposes a substitution or new time; the sender approves via a token link before capture.
- Auto-accept setting; alert jobs for orders not accepted within X minutes and for holds about to expire. Card holds last ~7 days, PayPal 10 days (extendable to 20), Klarna 28 days.
- Every change writes an OrderEvent (who, when, from, to, payload).
- Order captures:
  - sender (name, email, phone E.164, country, locale)
  - recipient (name, phone, address, CAP, address type HOME/OFFICE/HOSPITAL/FUNERAL_HOME/HOTEL, notes)
  - card message (length limit), hide_sender
  - delivery type/date/slot, rider
  - photos, items (product + variant snapshot: name, tier, price at time of order)
- Tracking: GET /orders/track/{token} returns a public-safe view (no sender email, no payment details).

E) Payments (Stripe), behind a PaymentProvider interface so a Mollie adapter could be added later
- Checkout:
  - PaymentIntent in EUR, capture_method=manual for website orders, automatic for payment requests
  - automatic_payment_methods enabled (cards, Apple Pay, Google Pay, PayPal, Klarna)
  - metadata: order_id and order number
  - statement descriptor suffix ROMAFIORITA
  - idempotency keys on every Stripe call
- Webhooks (/v1/webhooks/stripe):
  - verify the signature
  - store each event id (unique) for idempotency; process asynchronously; return 2xx fast
  - handle: payment_intent.amount_capturable_updated, payment_intent.succeeded, payment_intent.payment_failed, payment_intent.canceled, charge.refunded, charge.dispute.created/closed, payout.paid/failed
  - never trust redirect results alone; the webhook is the source of truth
- Admin money actions (OWNER/MANAGER only, audited, idempotent): capture, cancel hold, full/partial refund with reason.
- Admin payments API:
  - payments list (source: WEBSITE / PHONE / PAYMENT_REQUEST; status: held / captured / failed / refunded / disputed; fee and net, using the balance transaction)
  - held payments with time-to-expiry
  - refunds, payouts, balance, disputes with evidence deadline
  - monthly report (CSV), for the accountant
  - cache Stripe reads sensibly; paginate through the Stripe API

F) Custom-order payment requests (anti-scam, trust-first)
- Admin creates a request:
  - catalogue items (product + variant) and/or free-text custom items with a reference photo
  - recipient, delivery, card message, sender contact, locale
  - optional discount
  - expiry (default 48h)
- The server computes the total and creates the order in PAYMENT_REQUESTED with a 32+ byte random token. Store only a hash of the token.
- Public endpoints:
  - GET /v1/pay/{token}: summary, expiry, status; noindex
  - POST /v1/pay/{token}/intent: server-created PaymentIntent, automatic capture
  - POST /v1/verify: order number + email → confirms whether the request is genuine (rate-limited, no data leaks)
- Lifecycle: sent → viewed (record the first-viewed time) → paid → enters the normal lifecycle at ACCEPTED; or expired/cancelled. Editing before payment regenerates the token.
- Branded PDF "Order summary / Payment request" (WeasyPrint or similar):
  - logo, order number, items with photos, delivery details, total, link + QR, expiry, business contacts from settings
  - the title is configurable
  - it must NOT be labelled a fiscal invoice ("fattura"), because there is no VAT number yet
- Pre-filled WhatsApp text (wa.me link) and branded email templates, IT and EN.
- Optional reminder job 24h before expiry.

G) Notifications & jobs (arq + cron)
- Emails (IT/EN, Resend, from ordini@romafiorita.com):
  - order received, accepted, accept-with-change approval
  - bouquet photo, out for delivery, delivered
  - declined/refunded
  - payment request, request reminder
  - occasion reminders (7 and 2 days before)
  - abandoned checkout
- All sending is async with retries, backoff and dead-letter logging; templates are versioned.
- Real-time admin events: GET /v1/admin/orders/stream (SSE, authenticated, heartbeat, Redis pub/sub so it works across instances); plus Web Push subscriptions.
- WhatsApp Business API adapter behind a feature flag (off by default).

H) Uploads
- R2 signed PUT URLs: allowed MIME types, max size, server-generated keys.
- After upload, validate and strip EXIF location data; generate thumbnails (worker).
- Bouquet photos are linked to orders and served via signed or unguessable URLs.

I) Insights
- Google Search Console via a service account: clicks, impressions, CTR, position, top queries, landing pages, tracked keywords, sitemap/indexing status.
- Cached daily by a cron job into tables; admin endpoints read from the cache with a range parameter.
- Own sales analytics from our DB:
  - revenue per day
  - by occasion, tier, delivery type, sender country
  - new vs repeat customers
  - on-time %

J) Content & settings
- FAQs, cities/neighbourhood landing data (cut-off, fee, CAPs covered, notes), business identity (company name, address, VAT number, PEC, phone, WhatsApp) are all editable in settings.
- Business identity fields are nullable; the API returns null until the client provides them.
- Reviews: store only REAL reviews (with source and date). No seeded fake ratings or counts in production data or fixtures that could ship.

5. SECURITY & COMPLIANCE
══════════════════════════════════════
- Auth (admin):
  - email + password hashed with argon2
  - short-lived JWT access token + rotating refresh token in httpOnly, Secure, SameSite=Lax cookies, scoped to .romafiorita.com
  - CSRF protection for cookie-authenticated mutations
  - login rate limiting and lockout
  - optional TOTP 2FA for OWNER
- Roles: OWNER, MANAGER, FLORIST, RIDER. Enforce with dependencies on every admin route.
  - FLORIST/RIDER: only operational order data, no payments, no customer emails beyond what the task needs
  - RIDER: only orders assigned to them
- Object-level authorisation tests (no IDOR).
- CORS: only https://romafiorita.com, https://www.romafiorita.com, https://admin.romafiorita.com (+ localhost in dev).
- Security headers. Request size limits. Rate limits (Redis) on public endpoints, especially checkout, verify, pay, delivery/check and reminders.
- Validate everything with Pydantic: strict types, max lengths, E.164 phones, CAP format, emails.
- GDPR:
  - data minimisation; retention jobs (e.g. anonymise recipient addresses and messages after N months; configurable)
  - export/delete customer data endpoints for the OWNER
  - marketing consent stored separately
  - consent required for any recipient photo used in marketing
- Never store card data (Stripe only). Secrets only in env. Dependency audit in CI.
- Legal text: terms of sale must include the perishable-goods exclusion from the 14-day withdrawal right, the substitution policy and all-in prices. Expose versioned legal documents via the content API.
